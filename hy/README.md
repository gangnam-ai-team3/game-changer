# hy — 수집 담당 파트

담당자: 정현예

Anthropic API(Claude)를 쓰지 않고, 스팀 공식 API + 로컬 계산만으로 끝나는 파이프라인입니다.

## 파일 구성

| 파일 | 역할 | Claude API 사용 |
|---|---|---|
| `steam-db.js` | 스팀 게임 검색 + 로컬 DB(SQLite) 접근 공용 함수 | ❌ |
| `collector.js` | 스팀 공식 리뷰 API에서 전체 리뷰를 언어권별 병렬로 수집해 DB에 적재 | ❌ |
| `prepare-evidence.js` | **hy 담당 파트의 핵심.** 기간 필터 → 비식별화 → 너무 짧은 리뷰 삭제 → 근접중복 병합 → 벡터화 | ❌ |
| `call-agent.js` | (선택 사용, 독립 스크립트) `prepare-evidence.js`의 결과 위에 Claude로 사람이 읽는 보고서 문서까지 만듦. 기본 서버(`server.js`)에는 연결돼 있지 않음 | ✅ (여기만) |
| `export-anon-db.js` | 원본 DB에서 **공유해도 안전한 파생 스냅샷**(`evidence` 스키마 v2)을 만듦 | ❌ |
| `server.js` | `screen.html` 화면과 `prepare-evidence.js`를 잇는 로컬 서버(127.0.0.1 전용) | ❌ |
| `screen.html` | 테스트용 화면 | - |
| `steam-reviews.db` | 수집된 **원본** 리뷰 DB(SQLite, steamid·리뷰 원문 있음). 로컬 전용 데이터 — 절대 공유 금지, git에도 안 올림(`.gitignore`), 파일 권한 0600 | - |
| `steam-reviews.anon.db` | `export-anon-db.js`가 만든 **비식별 파생 스냅샷**(v2 스키마). 공유해도 안전하지만 git엔 못 올림(Release로만) | - |
| `.hash-salt` | 작성자 비식별화(`authorHash`)에 쓰는 비밀 소금값. **이게 새면 비식별화가 무효화되므로 절대 공유 금지**, git에도 안 올림 | - |
| `.evidence-key` | 공유용 스냅샷의 `evidence_id`를 만드는 데 쓰는 별도의 비밀 로컬 키. 이것도 절대 공유 금지, git에도 안 올림 | - |
| `*.test.js` | `node:test` 기반 자동 테스트. `npm test`(또는 `npm test --prefix hy`)로 실행 | - |

## 파이프라인

```
① 수집 (collector.js, 사람이 수동 실행)
   스팀 공식 appreviews API → 언어권 31개 병렬 → steam-reviews.db
   응답의 success/reviews/cursor 형식을 검증하고, 429/500/503/타임아웃만 제한적으로 재시도합니다.
   오류가 있었던 언어는 "완료(done=1)"로 저장하지 않습니다.

   node collector.js [분]        → 백필(처음부터 끝까지, 이미 끝난 언어는 자동 건너뜀)
   node collector.js sync [분]   → 동기화. 지난번 sync가 오류 없이 끝났을 때 저장해 둔 "경계 ID"까지만
                                    훑고, 새 리뷰는 삽입·이미 아는 리뷰는 내용이 바뀌었을 수 있어 UPSERT로
                                    갱신합니다. 도중에 오류가 나면 경계 ID를 갱신하지 않으므로, 다음 실행이
                                    실패한 구간을 처음부터 다시 훑어 누락을 회복합니다.
                                    나중에 하루 1회 / 1시간 1회로 자동 반복하려면 이 sync 모드를
                                    cron 같은 외부 스케줄러로 주기 실행하면 됨(이 파일 자체는 상시로
                                    계속 도는 프로세스가 아니라 실행할 때마다 한 번 돌고 끝남)

② 기간 필터 (prepare-evidence.js)
   사용자가 지정한 기간(periodStartMs~periodEndMs)에 해당하는 리뷰만 DB에서 조회.
   시작은 포함(>=), 기준일(periodEndMs)은 제외(<) — 작성일뿐 아니라 수정일도 기준일 이후면 제외합니다
   (더 이전에 써놓고 기준일 지나서 고친 리뷰가 섞여 들어가지 않도록).

③ 비식별화 (prepare-evidence.js)
   DB에서 꺼내는 즉시 작성자(steamid)를 단방향 해시(authorHash)로 치환 — 이후 단계는 이 해시만 다룹니다.

④ 너무 짧은 리뷰 삭제 + 근접중복 병합 (prepare-evidence.js)
   - 너무 짧은 리뷰는 통째로 제외 (기준은 아래 "최소 글자수 기준" 참고)
   - 남은 리뷰끼리: 완전히 같은 텍스트는 먼저 해시로 즉시 병합 → 그다음 같은 언어권 안에서 작성 시각
     순으로 정렬한 뒤 인접한 일부 구간만 문자 3-gram 자카드 유사도 90% 이상인지 비교해 병합
     (리뷰가 아주 많은 언어권에서 전부를 서로 비교하면 너무 느려지므로, 비교 범위와 총 비교 횟수에
     상한을 둡니다 — 상한에 걸리면 결과에 `dedupTruncated: true`로 표시됩니다)

⑤ 벡터화 (prepare-evidence.js)
   병합 후 남은 리뷰마다 64차원 숫자 벡터 생성(해싱 트릭 — 신경망 아님, 순수 계산)
```

`prepare-evidence.js`의 `prepareEvidence()` 함수 하나를 부르면 ②③④⑤가 한 번에 실행되고,
언어권별 건수 요약 + 최종 벡터화된 근거 배열을 돌려줍니다. 조회 시작일이 기준일보다 늦거나 같으면
요청 자체를 거부합니다. 지금은 PUBG: BATTLEGROUNDS(appid `578080`)만 수집하므로, 다른 게임이
들어오면 "리뷰 0건이라 완료됨"처럼 착각하기 쉬운 결과 대신 지원하지 않는 대상이라고 알려줍니다.

## 수집 상태(collectionStatus) — 단순 boolean이 아니라 네 가지

| 값 | 의미 |
|---|---|
| `complete` | 이 언어권이 요청 기간까지 완전히 수집됨(또는 이미 끝까지 백필 완료) |
| `partial` | 지난 수집/동기화 실행에서 오류가 있었음 — 일부만 믿을 수 있음 |
| `incomplete` | 아직 요청 기간까지 수집이 안 끝남(더 과거 쪽) |
| `unknown` | 이 언어권에 대한 수집 상태 기록 자체가 없음(한 번도 수집 안 함) |

리뷰가 0건이라는 이유만으로 "완료됨"이라고 판단하지 않습니다. 판단 근거가 된 값(`appId`, `oldestReachedAt`
— 과거 수집이 도달한 가장 오래된 시각, `lastSyncedAt` — 마지막으로 성공한 동기화 시각, `snapshotAt` —
지금 이 응답을 만든 시각)도 언어권별 요약에 그대로 같이 나갑니다.

**삭제된 리뷰 처리 정책**: 스팀에서 원작성자가 리뷰를 지워도, 이 DB는 그 사실을 스스로 알아채지
못합니다(스팀 API가 "삭제됨" 신호를 따로 주지 않음). `sync` 모드가 다음에 그 리뷰를 다시 마주치지
않으면 DB엔 계속 남아있습니다 — MVP 단계에선 이를 감수하고, 재검증이 필요하면 `collector.js`를
백필 모드로 다시 돌려 스냅샷을 통째로 새로 만드는 방식으로 대응합니다(개별 삭제 감지 기능은 아직 없음).

## 최소 글자수 기준 (④에서 "너무 짧다"의 기준)

기준값은 `prepare-evidence.js`의 `CJK_MIN_TEXT_LENGTH` / `DEFAULT_MIN_TEXT_LENGTH` 상수에 있습니다.
숫자를 바꾸면 이 표도 같이 고쳐야 합니다.

| 언어권 | 최소 글자수 | 이유 |
|---|---|---|
| 한국어(koreana), 중국어 간체(schinese), 중국어 번체(tchinese), 일본어(japanese) | **8자** | 음절/한자 하나에 뜻이 압축돼 있어, 짧아도 완결된 문장인 경우가 많음 (실측: "핵쟁이 진짜 많아요" 10자, "外挂太多了真的" 7자, "チーターが多すぎる" 9자 — 전부 완결된 문장) |
| 그 외 언어(영어 등 나머지 27개) | **20자** | 같은 뜻이라도 알파벳 기반 언어는 훨씬 더 많은 글자가 필요 (예: "too many cheaters" 17자) |

이 미만인 리뷰는 최종 결과(`evidence`)에서 아예 빠집니다(중복 비교 대상에서도 제외).

## 중복 병합 기준

세 가지 기준 중 하나라도 걸리면 같은 그룹으로 병합합니다.

- **완전 동일 텍스트**: 정규화한 텍스트가 완전히 같으면 즉시 병합(해시 기반, 빠름)
- **텍스트 유사도**: 같은 언어권 안에서, 작성 시각이 가까운 구간끼리만 문자 3-gram 자카드 유사도 **90% 이상**(번역돼서 다른 언어로 재게시되는 경우는 범위 밖). 리뷰가 매우 많은 언어권은 비교 범위·횟수에 상한이 있어 일부를 못 볼 수 있습니다(`dedupTruncated`로 표시)
- **작성자+시간창**: 같은 작성자(아래 "비식별화" 참고)가 **30분 이내**에 또 올린 경우 (`AUTHOR_TIME_WINDOW_SECONDS`, `prepare-evidence.js`) — 표현을 완전히 바꿔 다시 써서 텍스트 유사도로는 못 잡는 경우를 보완

그룹 안에서는 텍스트가 가장 긴(정보가 많은) 리뷰를 대표로 남기고, 나머지는 `mergedIds`에 기록, `duplicateCount`로 개수 표시

## 비식별화 — steamid는 결과에 남지 않음

DB에는 원본 steamid가 있지만, `prepareEvidence()`를 거치면 즉시 **단방향 해시**(SHA-256 + 비밀 소금값, 앞 16자)로 치환되어 `authorHash` 필드로만 나갑니다. 같은 사람이 쓴 건지 판단(중복 병합용)은 여전히 가능하지만, 해시값만으로 원래 스팀 계정을 역으로 알아낼 수는 없습니다. 최종 `evidence`에는 원본 `steamid`가 전혀 포함되지 않습니다.

소금값(`hy/.hash-salt`)은 처음 실행할 때 자동으로 무작위 생성되어 로컬에 저장되고, 이후로는 계속 같은 값을 씁니다(그래야 같은 사람이 언제 다시 조회해도 같은 해시가 나옴). steamid는 형식이 정해진 숫자(예: `7656119`로 시작하는 17자리)라서, 소금 없이 그냥 해시만 하면 공격자가 있을 법한 steamid를 미리 다 해시해 둔 표로 역추적할 수 있습니다 — 그래서 소금을 반드시 섞고, 이 파일은 어디에도 공유하지 않습니다. 파일이 64자리 hex 형식이 아니면(손상됐으면) 조용히 쓰지 않고 새로 만듭니다.

**원본 `steamid` 자체는 원본 DB(`steam-reviews.db`)에 계속 보관합니다** — 나중에 특정 리뷰가 진짜 계정이 쓴 건지 실제 스팀 프로필에서 직접 확인해야 할 수 있어, 의도적으로 남겨두는 결정입니다. 그만큼 이 파일은 로컬 전용이고, DB·WAL·SHM 파일 권한을 0600으로 좁혀 접근을 제한합니다(폴더 전체를 0700으로 좁히진 않습니다 — `hy/` 폴더엔 다른 소스 코드도 같이 있는 공용 공간이라, DB 파일 자체만 잠급니다).

## 공유할 땐 원본이 아니라 안전한 파생 스냅샷을 만들어서

원본 DB(`steam-reviews.db`)는 **한 번 밖으로 나가면 되돌릴 수 없으므로** 절대 공유하지 않습니다.

```
node export-anon-db.js
```

를 실행하면 `steam-reviews.anon.db`(v2 스키마)가 만들어집니다.

**v2로 바뀐 이유**: 예전 v1은 steamid만 `author_hash`로 바꾸고 `recommendationid`·리뷰 원문·정확한
타임스탬프는 그대로 남겼습니다. 그런데 스팀 공식 `appreviews` API는 `recommendationid`와 실제
`author.steamid`를 같은 응답 객체로 묶어서 돌려줍니다(우리가 `collector.js`에서 이렇게 수집함) —
즉 누구든 우리처럼 같은 공개 API를 다시 돌리기만 하면 `recommendationid → steamid` 대조표를 만들 수
있어서, steamid를 지워도 사실상 재식별이 가능했습니다. (이 문제로 예전에 올렸던 v1 Release는
삭제했습니다.)

v2는 그래서 "판단 가능한 최소 정보"만 남깁니다:

| 필드 | 설명 |
|---|---|
| `evidence_id` | 로컬 전용 키(`.evidence-key`)로 만든 HMAC-SHA256 앞 24자리. `recommendationid`나 키 둘 다 파일에 없어 되돌릴 수 없음 |
| `app_id` | 578080(PUBG) |
| `language` | 스팀 언어 코드 |
| `created_at` / `updated_at` | UTC **날짜 단위**로만(시:분:초 없음 — 정확한 시각까지 남으면 스팀 공개 리스트와 대조해 역추적될 위험이 있음) |

리뷰 원문·`recommendationid`·`steamid`·`author_hash`·재생시간은 스키마에도 파일 바이트 어디에도
없습니다. **의미 판단(긍정/부정, 요약, 원인 분류 등)이 필요한 필드는 이 스냅샷에 없습니다** — 그건
jelly 파트가 만드는 값이고, jelly·res 담당자와 계약을 먼저 맞춘 뒤에 별도로 합류시킬 예정이라
지금은 의도적으로 얇은(thin) 스냅샷입니다.

이 사본은 여전히 진짜 SQLite DB라서, `prepareEvidence({ ..., dbPath: './steam-reviews.anon.db' })`처럼
자유롭게 기간·언어를 바꿔가며 집계 조회는 가능합니다(다만 v2엔 리뷰 원문이 없어 문장 단위 근거 확인은
원본 DB에서만 가능). 용량은 원본보다 작지만(200MB 안팎) 여전히 git 100MB 제한을 넘어 **GitHub Release
첨부**로만 공유합니다.

`export-anon-db.js`는 출력 경로가 원본 DB와 같으면(경로 문자열 비교 + inode 비교) 실행 자체를
거부합니다. 내보내기는 임시 파일에 완성한 뒤 검증을 통과해야만 `rename`으로 활성 파일 자리에 원자
교체되므로, 도중에 실패해도 기존 원본이나 기존 활성 사본이 그대로 유지됩니다.

## 보존 기간과 삭제

원본 DB는 자동 만료 없이 로컬 기기에 계속 보관됩니다. 지우려면:

```
rm hy/steam-reviews.db hy/steam-reviews.db-shm hy/steam-reviews.db-wal
```

지우면 그 이후로는 예전 리뷰에 대한 steamid 수동 조회도 함께 불가능해집니다(다시 수집해도 스팀이
이미 지워진 리뷰까지 복원해 주진 않음).

## 벡터화 방식

신경망 임베딩이 아니라 **해싱 트릭**(scikit-learn의 HashingVectorizer와 같은 원리)입니다.
리뷰 텍스트의 3-gram을 64차원 숫자 벡터로 접어넣고 L2 정규화합니다. 모델 다운로드나 외부 API가 없어
메모리 부담이 거의 없고, 텍스트 밖으로 나가는 정보도 없습니다. "글자 조합이 얼마나 겹치는지"만 보는
통계적 벡터라, 의미(동의어·패러프레이즈) 기반 검색이나 신경망 임베딩과 같은 용도로 쓸 수는 없습니다.

## 서버 API (server.js)

`node server.js` 실행 후 `http://127.0.0.1:8787`(로컬 전용 — 외부 네트워크에서 접근 불가):

| 경로 | 하는 일 | Claude API |
|---|---|---|
| `GET /` | `screen.html` 반환 | - |
| `POST /evidence` | `prepareEvidence()` 직접 호출 — 언어권별 요약 + 벡터화된 근거 반환 | ❌ |

- 요청 본문은 `Content-Type: application/json`만 허용, 최대 2MB(넘으면 413)
- 처리 시간이 30초를 넘으면 504로 중단(너무 넓은 기간·언어 요청이 서버를 오래 붙잡지 않도록)
- 응답에는 **리뷰 원문과 `authorHash`를 담지 않습니다**(로컬 전용 서버라도 원칙을 지킴) — `screen.html`은
  건수·날짜·추천여부 같은 메타 정보만 보여줍니다. 원문을 직접 보려면 로컬에서 DB를 직접 조회하세요.
- `POST /call-agent`는 이번 개정에서 기본 서버 경로에서 **제거**했습니다. `call-agent.js`는 여전히
  독립 스크립트로 남아있고, 필요하면 직접 실행하세요(Claude API 키 필요, 선택 사항).

`node:test` 기반 자동 테스트가 실행됩니다(실제 스팀 API나 Claude API를 호출하지 않고, 가짜 응답과
임시 SQLite DB로 검증합니다).

## 알아둘 점 — 키워드/의미 분류는 이 단계에 없음

이벤트/키워드가 리뷰와 "의미상" 관련 있는지 판단하거나, 긍정/부정/원인 같은 분류를 매기는 건 이
파트의 범위가 아닙니다. 그건 jelly 파트가 하는 일과 겹치고 의미 판단에는 AI가 필요해서, 이 README가
다루는 순수 로컬 파트는 기간·비식별화·길이·중복만 다룹니다. 사람이 읽는 보고서까지 필요하면
`call-agent.js`(Claude 사용, 선택적 독립 스크립트)가 이 파트의 결과 위에서 처리합니다.
