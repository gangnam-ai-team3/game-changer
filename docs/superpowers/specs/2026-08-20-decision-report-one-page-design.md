# 게임체인저 한 페이지 출시 판단 보고서 설계

## 1. 결정 요약

게임체인저의 이벤트 점검과 업데이트 점검 결과를 같은 형식의 한 페이지 보고서로 정리한다. 사용자는 결과 화면의 첫 구간만 읽어도 무엇을 검토했는지, 어떤 반응이 예상되는지, 가장 큰 위험이 무엇인지, 출시 전에 무엇을 해야 하는지 판단할 수 있어야 한다.

기존 화면에 있는 상세 근거와 멀티에이전트 실행 과정은 삭제하지 않는다. 핵심 판단 아래의 세 개 상세 영역으로 이동하고 기본 상태를 접힘으로 바꾼다. 실행 중에는 에이전트 진행 화면을 펼쳐 두고, 결과가 나오면 보고서가 주 화면이 되도록 실행 과정을 접는다.

이 변경은 프론트엔드 정보 구조와 표현 방식만 다룬다. 백엔드 계약, 위험 판정 정책, 근거 ID, 최종 판정 값은 변경하지 않는다.

## 2. 배경과 문제

현재 결과 화면은 판정 요약, 예상 반응, 이용자 유형, 언어권, 위험, 개선안, 에이전트 과정과 계약 JSON을 한 화면에 연속해서 표시한다. 같은 문장과 같은 위험이 여러 구간에서 반복되고, 핵심 결론보다 상세 카드가 먼저 시선을 끈다. 이용자는 정보를 많이 볼 수 있지만 다음 질문에 바로 답하기 어렵다.

- 이번 기획은 출시해도 되는가
- 이용자는 어떤 점을 기대하거나 우려하는가
- 판정을 좌우한 위험은 무엇인가
- 출시 전에 무엇을 확인하거나 수정해야 하는가
- 이 판단은 어떤 근거와 에이전트 처리 과정에서 나왔는가

결과 화면의 목적을 정보 나열에서 의사결정 지원으로 바꾼다. 핵심 정보는 항상 보이고, 검증용 세부 정보는 사용자가 필요할 때 펼쳐 보는 구조가 적합하다.

## 3. 목표와 제외 범위

### 3.1 목표

- 이벤트 점검과 업데이트 점검의 결과 화면을 같은 보고서 구조로 통일한다.
- 판정, 예상 반응, 주요 위험, 출시 전 조치를 한 화면에서 파악할 수 있게 한다.
- 위험과 조치, 확인 지표를 ID로 연결해 의미가 맞는 항목끼리 보여준다.
- 이용자 의견, 언어권 결과, 근거, 에이전트 산출물을 상세 영역에서 계속 확인할 수 있게 한다.
- 기본 보고서와 이용자 유형 카드 사이에서 같은 대표 의견과 설명이 반복되지 않게 한다.
- 1440×900 데스크톱 화면에서는 헤더, 핵심 카드, 위험과 조치 표가 첫 화면에 들어오고, 390픽셀 모바일 화면에서는 가로 스크롤 없이 한 열로 읽히게 한다.
- 키보드 탐색, 초점 표시, 상태 이름을 포함한 기본 접근성을 유지한다.

### 3.2 제외 범위

- 백엔드 계약과 판정 정책은 바꾸지 않는다.
- 이벤트 자료에 없는 긍정 또는 부정 감정 값을 새로 추론하지 않는다.
- 감정 비율 차트와 새 데이터 시각화 라이브러리를 추가하지 않는다.
- PDF 저장, 파일 내보내기, 인쇄 전용 화면은 이번 범위에 포함하지 않는다.
- 에이전트 계약 JSON을 하나의 공통 컴포넌트로 다시 만드는 작업은 하지 않는다.
- 입력 화면과 자료 수집 방식은 변경하지 않는다.

## 4. 정보 구조

결과 보고서는 다음 순서로 구성한다.

### 4.1 보고서 헤더

항상 표시하는 정보는 다음과 같다.

- 검토 대상 이름
- 출시 판단 배지
- 한 문장 결론
- 사용한 자료 범위 한 줄
- 자료 또는 핵심 분석이 실제로 미완료된 경우에만 표시하는 주의 안내

한 문장 결론은 전체 `executive_summary`를 그대로 반복하지 않는다. 판정을 내린 이유와 가장 먼저 해야 할 조치를 한 문장으로 결합한다. 연결된 조치가 없으면 확인되지 않은 내용을 만들지 않고 판정 이유만 표시한다.

판정 이유는 `validated.decision_reason`만 사용한다. 이벤트와 업데이트의 프론트 응답 타입에 `decision_reason`을 명시해, 장문의 `executive_summary`를 잘라 쓰거나 화면에서 새 이유를 추론하지 않는다.

검토 대상 이름은 현재 편집 중인 입력값을 바로 참조하지 않는다. 요청을 보낼 때 이벤트명 또는 업데이트명을 제출값으로 보존하고, 해당 요청의 결과와 함께 저장한 이름을 보고서 제목으로 사용한다. 결과가 나온 뒤 입력란을 수정해도 이미 생성된 보고서 제목은 바뀌지 않는다.

`analysis_incomplete=true`일 때만 자료 보강 안내를 헤더 아래에 표시한다. 선택형 에이전트가 실패했더라도 핵심 근거와 코드 판정이 완료됐다면 상단 판단을 약화하지 않는다. 이 경우 대체 처리 여부는 에이전트 실행 상세에서만 보여준다.

### 4.2 핵심 카드 세 개

첫 화면에는 높이가 같은 카드 세 개를 배치한다.

1. **예상 효과**
   - 업데이트 점검은 근거가 가장 넓게 연결된 긍정 신호를 보여준다.
   - 이벤트 점검은 감정 계약이 없으므로 `영향이 큰 이용자 반응`이라는 이름으로 표시한다. 가장 많은 근거가 연결된 이용자 유형의 예상 반응을 사용하며, 긍정 반응으로 표현하지 않는다.
2. **가장 큰 위험**
   - 정책이 정렬한 `top_risks[0]`을 사용한다.
   - 위험 제목, 등급, 이용자에게 발생할 수 있는 문제를 간결하게 표시한다.
3. **출시 전 조치**
   - 가장 큰 위험과 ID로 연결된 개선안 또는 권고안을 표시한다.
   - 함께 연결된 확인 지표가 있으면 조치 아래에 한 줄로 보여준다.

이용자 유형별 대표 의견의 직접 화법은 핵심 카드에서 사용하지 않는다. 핵심 카드에는 계약 필드의 제목, 영향 이용자, 연결된 위험과 예상 행동만 표시하고, 따옴표가 있는 이용자 유형별 대표 의견은 해당 상세 카드 가운데 한 곳에서만 보여준다.

프론트엔드가 자유문을 새 문장으로 다시 쓰지는 않는다. 업데이트 카드는 긍정 신호의 `title`, 영향 이용자 이름, 고유 근거 수를 사용한다. 이벤트 카드는 대표 이용자 유형 이름, 연결된 가장 큰 위험, 고유 근거 수를 사용한다. 두 모드 모두 자연어 필드에 `예상 행동:` 구간이 있으면 그 뒤의 문장만 보조 설명으로 표시하고, 구간이 없으면 제목과 연결 정보만 보여준다.

### 4.3 위험과 조치 표

핵심 카드 아래에는 최대 세 개의 상위 위험을 표로 표시한다.

| 열 | 표시 내용 |
|---|---|
| 위험 | 위험 제목 |
| 수준 | 한국어로 변환한 위험 등급 |
| 이용자에게 생길 수 있는 문제 | `failure_path`를 자연스러운 한국어로 표시 |
| 출시 전 확인 | 연결된 개선안과 확인 지표 또는 성공 기준 |

행은 백엔드의 `top_risks` 순서를 따른다. 위험이 없으면 빈 표를 만들지 않고 `현재 검증 범위에서 우선 위험이 확인되지 않았습니다`라는 한 줄 상태를 표시한다.

### 4.4 상세 영역 세 개

핵심 보고서 아래에는 기본적으로 접힌 상세 영역을 둔다.

1. **예상 반응과 이용자 유형**
   - 업데이트의 긍정, 우려, 반응이 갈릴 조건
   - 이벤트와 업데이트의 이용자 유형별 예상 반응 카드
2. **언어권과 판단 근거**
   - `판정 논리 전체 보기`에 기존 `executive_summary` 전문
   - 언어권별 결론과 표본 공개 여부
   - 근거 범위, 비식별 파생 요약, 연결된 위험과 확인 지표
3. **에이전트 실행 과정과 산출물**
   - 네 에이전트의 노드별 처리 과정
   - 대체 처리와 호출 상태
   - 기존 계약 JSON

각 영역은 기본 HTML `details`와 `summary`를 사용한다. 별도의 탭 상태 관리나 외부 UI 라이브러리는 추가하지 않는다.

## 5. 공통 컴포넌트 설계

새 공통 컴포넌트 `DecisionReport`가 보고서 헤더, 핵심 카드, 위험과 조치 표, 세 개 상세 영역의 배치를 맡는다. 이벤트와 업데이트 화면은 현재 계약을 보고서용 데이터로 변환한 뒤 공통 컴포넌트에 전달한다.

공통 데이터는 다음 의미를 갖는다.

| 필드 | 의미 |
|---|---|
| `subject` | 이벤트명 또는 업데이트명 |
| `decision` | `Go`, `Revise`, `Test`, `Hold` 가운데 해당 모드가 지원하는 값 |
| `decisionLabel` | 화면에 표시할 한국어 판정 |
| `conclusion` | 판정 이유와 우선 조치를 결합한 한 문장 |
| `fullReasoning` | `executive_summary` 전문 |
| `sourceScope` | 근거 수, 공개 가능한 언어권, 자료 범위를 요약한 한 줄 |
| `analysisIncomplete` | 실제 자료 또는 핵심 분석 미완료 여부 |
| `expectedCard` | 예상 효과 또는 영향이 큰 이용자 반응 |
| `riskCard` | 가장 큰 위험 |
| `actionCard` | 가장 먼저 해야 할 조치와 확인 기준 |
| `riskRows` | 상위 위험과 연결된 조치 목록 |
| `reactionDetails` | 예상 반응과 이용자 유형을 렌더링하는 `ReactNode` |
| `evidenceDetails` | 판정 논리, 언어권과 판단 근거를 렌더링하는 `ReactNode` |
| `agentDetails` | 에이전트 실행 과정과 산출물을 렌더링하는 `ReactNode` |

세부 콘텐츠까지 하나의 복잡한 공통 형식으로 바꾸지 않는다. 기존 `AudienceCards`, `AgentPipeline`, 각 화면의 `ArtifactDetails`를 그대로 재사용하고 `DecisionReport`의 세 개 상세 영역에 자식 콘텐츠로 전달한다. 이벤트와 업데이트 계약의 차이를 유지하면서 공통 화면만 통일하는 가장 작은 변경이다.

`DecisionReport`는 `fullReasoning`을 `언어권과 판단 근거` 영역 안의 중첩된 `판정 논리 전체 보기`로 먼저 렌더링한 뒤 `evidenceDetails`를 이어서 표시한다.

`DecisionReport`는 결과 제목의 참조와 마운트 뒤 초점 이동을 직접 관리한다. 이벤트와 업데이트 화면에 같은 `useEffect`와 제목 참조를 반복하지 않는다.

보고서용 변환 함수는 별도 추상화 파일을 만들지 않는다. 이벤트 변환은 `page.tsx`, 업데이트 변환은 `UpdateReview.tsx` 안의 순수 함수로 둔다. 구현이 실제로 반복된다는 근거가 생기기 전에는 공통 변환 계층을 추가하지 않는다.

## 6. 데이터 선택과 연결 규칙

### 6.1 공통 정렬 규칙

- 가장 큰 위험은 `top_risks[0]`이다. 프론트엔드에서 위험 등급이나 신뢰도로 다시 정렬하지 않는다.
- 같은 선택 단계 안에서는 `evidence_ids` 고유 개수가 많은 순서로 고른다.
- 근거 수가 같으면 `confidence`가 높은 항목을 선택한다.
- 두 값이 같으면 이용자 유형 ID의 오름차순으로 결정해 같은 입력에서 같은 결과가 나오게 한다.
- 근거 ID가 없는 이용자 유형은 대표 카드에서 제외한다. 상세에서는 `현재 자료로 판단하기 어려움` 상태로 표시할 수 있다.
- 신뢰도 백분율은 핵심 카드에서 사용하지 않는다. 상세 영역에서는 `근거 일치도`라는 이름으로 표시한다.

### 6.2 이벤트 점검 변환

- `subject`: 요청을 보낼 때 보존한 이벤트명
- `conclusion`: `validated.decision_reason`을 먼저 표시하고, 가장 큰 위험에 연결된 개선안이 있으면 `우선 조치는 ‘{revision.title}’입니다`를 덧붙인다.
- `expectedCard`: 먼저 가장 큰 위험 ID가 연결된 `panel_results`, 다음으로 다른 위험이 연결된 항목, 마지막으로 위험 연결이 없는 항목 순서로 후보를 좁힌 뒤 공통 정렬 규칙으로 선택
- `riskCard`: `top_risks[0]`
- `actionCard`: 가장 큰 위험의 ID를 `addresses_risk_ids`에 포함한 `revision_plan` 가운데 `priority`가 가장 낮은 항목
- `riskRows`: 각 위험 ID를 `addresses_risk_ids`에 포함한 `revision_plan` 가운데 `priority`가 가장 낮은 항목을 찾는다.
- `출시 전 확인`: 연결된 개선안의 `success_metric`
- `sourceScope`: `feedback.evidence`의 고유 근거 수, `language_results`에서 `conclusion`이 공개된 언어권 수, `feedback.input_mode`의 한국어 이름

이벤트 계약에는 감정 값이 없으므로 예상 효과 카드에 긍정 근거 수를 만들지 않는다. 대표 이용자 반응도 `영향이 큰 이용자 반응`으로 표현한다.

이벤트 대표 카드의 제목은 이용자 유형 이름으로 정한다. 본문은 연결된 가장 큰 위험과 고유 근거 수를 표시하고, `reaction`에서 `예상 행동:` 뒤의 문장을 찾을 수 있을 때만 예상 행동을 덧붙인다. 대표 의견 구간을 자동으로 간접 화법으로 바꾸지 않는다.

### 6.3 업데이트 점검 변환

- `subject`: 요청을 보낼 때 보존한 업데이트명
- `conclusion`: `validated.decision_reason`을 먼저 표시하고, 가장 큰 위험에 연결된 권고안이 있으면 `우선 조치는 ‘{recommendation.title}’입니다`를 덧붙인다.
- `expectedCard`: `expected_positive` 가운데 고유 근거 수가 많고, 그다음으로 `confidence`가 높으며, 마지막으로 `impact_id`가 앞선 항목
- `riskCard`: `top_risks[0]`
- `actionCard`: 가장 큰 위험의 ID를 `addresses_risk_ids`에 포함한 `recommendations` 가운데 `priority`가 가장 낮은 항목
- `riskRows`: 각 위험과 연결된 `recommendations` 가운데 `priority`가 가장 낮은 항목을 찾는다.
- `출시 전 확인`: 먼저 선택한 권고안의 `validation_metric_ids`로 `validation_metrics`를 찾고, 없으면 위험 ID를 `addresses_risk_ids`에 포함한 지표를 찾는다. 표에는 선택한 지표의 `success_condition`을 표시한다.
- `sourceScope`: `brief.evidence`의 고유 근거 수, `language_insights`에서 `conclusion`이 공개된 언어권 수, `feedback.input_mode`의 한국어 이름

확인 지표가 여러 개면 권고안에 기록된 ID 순서를 따른다. 연결 관계가 없는 첫 번째 배열 항목을 임의로 사용하지 않는다.

업데이트 예상 효과 카드의 제목은 선택한 `expected_positive.title`을 사용한다. 본문에는 `affected_personas`의 한국어 이름과 고유 근거 수를 표시하고, `summary`에서 `예상 행동:` 뒤의 문장을 찾을 수 있을 때만 예상 행동을 덧붙인다. 따옴표가 포함된 대표 의견 구간은 핵심 카드에 표시하지 않는다.

두 모드의 `sourceScope`에는 긍정과 우려 건수를 넣지 않는다. 이 값은 투표 수가 아니므로 상단 자료 범위에 배치하면 다수결로 오해할 수 있다.

`feedback.input_mode`가 없거나 알려진 값이 아니면 자료 방식은 생략한다. 내부 값을 그대로 사용자 화면에 노출하지 않는다.

### 6.4 연결 항목이 없을 때

프론트엔드는 없는 데이터를 만들어 내지 않는다.

- 가장 큰 위험이 없으면 위험 카드에 `우선 위험이 확인되지 않았습니다`를 표시한다.
- 위험과 연결된 조치가 없으면 `연결된 출시 전 조치를 확인할 수 없습니다`를 표시한다.
- 확인 지표가 없으면 `확인 기준이 연결되지 않았습니다`를 표시한다.
- 예상 효과 또는 근거가 연결된 이용자 유형이 없으면 `현재 근거만으로 대표 반응을 선정하기 어렵습니다`를 표시한다.

이 상태 문구는 판정 자체를 바꾸지 않는다. 실제 판정 보류는 백엔드의 `decision`과 `analysis_incomplete`를 그대로 따른다.

## 7. 결론 문장과 중복 방지

### 7.1 상단 결론

상단 결론은 다음 순서로 구성한다.

1. 판정을 좌우한 이유
2. ID로 연결된 우선 조치

가장 큰 위험은 결론 문장에 반복하지 않고 바로 아래의 `가장 큰 위험` 카드에서 보여준다.

길이는 데스크톱 두 줄 안을 목표로 한다. 전체 논리는 `언어권과 판단 근거` 상세 영역의 첫 항목인 `판정 논리 전체 보기`에서 기존 `executive_summary`를 그대로 확인할 수 있게 한다. 별도의 네 번째 상세 영역은 만들지 않는다.

상단 결론에는 근거 개수, 언어권 개수, 에이전트 이름을 모두 나열하지 않는다. 이 정보는 자료 범위 한 줄과 상세 영역에서 제공한다.

### 7.2 이용자 유형별 대표 의견

따옴표로 표현한 이용자 유형별 대표 의견은 이용자 유형 상세 카드에서만 표시한다. 예상 효과 카드, 상단 결론, 위험 표에서는 대표 의견을 재작성하지 않고 계약 제목과 연결 정보로 대체한다.

대표 의견을 공백과 문장부호 기준으로 정규화했을 때 같은 문장이 두 이용자 유형에 반복되면, 근거 수와 일치도가 높은 카드에만 원문을 표시한다. `PersonaGameCard`에는 `opinionVisible` 속성을 추가한다. 나머지 카드에는 예상 행동과 연결된 위험을 유지하고 `대표 의견은 관련 이용자 유형 카드에 함께 표시했습니다`라고 안내한다.

중복 방지 범위는 기본 보고서와 이용자 유형 카드 사이의 대표 의견이다. 언어권 카드는 언어권별 맥락을 비교하는 영역이므로 이번 중복 제거 범위에서 제외한다. 감사 목적으로 접어 둔 `executive_summary` 전문도 원본 보존이 우선이므로 예외로 둔다.

### 7.3 자료 수의 의미

긍정, 우려, 혼합 근거 수는 이용자 투표가 아니라 해당 신호에 연결된 근거 구성이다. 핵심 화면에 비율 막대나 우세 비율을 표시하지 않는다. 필요하면 상세 영역에서 건수와 의미를 함께 설명한다.

## 8. 상태와 오류 처리

### 8.1 실행 중

- `AgentPipeline`을 펼친 상태로 표시한다.
- 현재 처리 중인 노드만 강조한다.
- 완료된 노드는 완료 상태, 아직 시작하지 않은 노드는 대기 상태로 구분한다.
- 화면 읽기 도구에는 현재 노드 변경만 짧게 알린다.

### 8.2 결과 완료

- 결과가 도착하면 `DecisionReport`로 초점을 이동한다.
- 에이전트 실행 과정은 접힌 상세 영역으로 이동한다.
- `fallback_used=true`이고 `analysis_incomplete=false`이면 상단에 경고를 표시하지 않는다. 대체 처리 사실과 해당 단계는 실행 상세에서 확인한다.
- `analysis_incomplete=true`이면 상단에 자료 또는 핵심 분석 미완료 안내를 표시한다.

### 8.3 오류

- 결과 계약이 없을 정도의 요청 실패는 기존 오류 영역을 유지하고 보고서를 표시하지 않는다.
- 일부 표시 데이터의 연결이 누락돼도 화면 전체를 실패시키지 않는다. 6.4절의 확인 문구를 해당 위치에 표시한다.
- 판정 값이 알려진 목록에 없으면 원본 값을 그대로 노출하지 않고 `판정 확인 필요`로 표시한다. 개발용 원본은 계약 JSON에서 확인한다.

## 9. 시각 원칙

- Linear Design System의 절제된 보고서 느낌을 유지한다.
- 흰색과 중립 회색을 기본으로 사용하고, 판정과 위험 등급에만 상태 색상을 적용한다.
- 세 핵심 카드는 같은 높이와 같은 내부 여백을 사용한다.
- 제목, 결론, 카드, 표, 상세 영역 순서로 정보 위계를 분명히 한다.
- 위험과 조치는 카드 묶음이 아니라 비교 가능한 표로 보여준다.
- 핵심 본문은 14픽셀 이상, 보조 문구는 12픽셀 이상으로 표시한다.
- 데스크톱은 세 열, 모바일은 한 열로 바꾼다.
- 그림자와 장식 효과는 최소화한다. 상태를 강조하기 위해 카드 전체를 강한 색으로 채우지 않는다.
- 색상만으로 판정과 위험을 구분하지 않는다. 항상 한국어 상태 이름을 함께 표시한다.

## 10. 접근성

- 보고서 제목은 결과 영역의 최상위 제목으로 두고 `tabIndex={-1}`을 유지해 결과 도착 후 초점을 받을 수 있게 한다.
- 핵심 카드에는 각각 제목이 있어 화면 읽기 도구로 구분할 수 있어야 한다.
- 위험과 조치 목록은 실제 `table`, `thead`, `tbody` 요소를 사용한다. 모바일에서도 열 제목의 의미가 사라지지 않게 한다.
- 390픽셀 화면에서는 각 행을 세로로 쌓되 각 값에 열 제목을 함께 표시해 가로 스크롤 없이 의미를 유지한다.
- 상세 영역은 기본 `details`와 `summary`를 사용해 키보드로 열고 닫을 수 있게 한다.
- 초점 테두리는 배경과 충분히 대비되는 불투명 색상을 사용한다.
- 실행 상태는 색상 외에 `작업 중`, `완료`, `대기`, `대체 처리` 문구를 함께 표시한다.

## 13. 수용 기준

- 이벤트와 업데이트 결과가 같은 보고서 순서와 시각 위계를 사용한다.
- 1440×900 데스크톱 첫 화면에 판정, 예상 반응, 가장 큰 위험, 출시 전 조치가 함께 보인다.
- 390픽셀 모바일 화면에서는 가로 스크롤 없이 한 열로 표시된다.
- 상단 결론은 기존 장문 요약을 반복하지 않고 판정 이유와 우선 조치를 전달한다.
- 위험과 조치, 확인 지표가 ID로 정확히 연결된다.
- 기본 보고서와 이용자 유형 카드 사이에서 같은 대표 의견이 반복되지 않는다. 언어권 카드와 감사용 `executive_summary` 전문은 예외다.
- 상세 근거와 멀티에이전트 과정은 삭제되지 않고 기본 접힘 상태로 제공된다.
- 선택형 에이전트 대체 처리는 핵심 분석이 완료된 판정을 `Hold`처럼 보이게 만들지 않는다.
- 실제 자료 또는 핵심 분석이 미완료된 경우에만 보강 안내가 나타난다.
- 기존 프론트엔드 계약 검사와 프로덕션 빌드가 통과한다.
