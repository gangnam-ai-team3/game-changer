# 게임체인저 출시 전 업데이트 점검 설계

## 1. 결정 요약

게임체인저는 기존의 이벤트 출시 전 점검과 별도로, 게임 업데이트·변경안의 출시
전 이용자 반응을 예상하는 `업데이트 점검` 모드를 제공한다. 첫 목표는 과거의
실제 업데이트를 다시 실행하는 것이 아니라, 과거 사례를 안정적인 저장 시연
데이터로 사용해 새 분석 흐름을 검증하는 것이다.

기본 시연은 저장된 합성 데이터로 수행한다. 저장 데이터는 공식 패치 노트와
공개된 사후 맥락을 바탕으로 만들되, 실제 사용자 원문이나 실제 여론으로
표현하지 않는다. Steam·X 실시간 수집은 사용자가 별도로 선택했을 때만 실행하며,
수집 실패·표본 부족·비용 초과는 기본 시연과 분리한다.

출시 전 결과는 실제 반응이 아니라 기획 조건과 근거에서 도출한 예상이다. 화면은
다음 세 층을 명확히 구분한다.

1. **출시 전 예상**: 긍정 반응, 부정 반응, 반응이 갈릴 이용자 유형
2. **출시 판단**: 출시 가능, 일부 수정 후 출시, 테스트 후 출시, 판정 보류
3. **검증 지표**: 출시 후 실제로 확인할 긍정·부정 반응과 행동 지표

## 2. 목표와 제외 범위

### 2.1 목표

- 이벤트 점검 기능을 유지하면서 업데이트 점검을 별도 모드로 제공한다.
- 무기 밸런스, UI·UX, 시스템·규칙 업데이트를 공통 입력 흐름에서 다룬다.
- 과거 업데이트 저장 사례를 선택해 같은 입력에서 같은 핵심 판정을 재현한다.
- 예상 긍정·부정 반응을 근거 ID와 연결해 보여준다.
- 출시 전 판단과 출시 후 검증 지표를 화면에서 섞지 않는다.
- 실시간 Steam·X 수집은 별도 선택 경로로 제공하고, 원문을 저장하지 않는다.
- 기존 멀티에이전트의 중간 결과·노드·정의된 값·자연어 설명 표시 방식을 재사용한다.

### 2.2 1차 저장 사례

**Dragunov 확률 피해 제거 업데이트**를 첫 저장 사례로 사용한다.

- 이전 상태: 피해가 기본 58, 최대 73으로 달라지는 확률형 피해 구조
- 변경안: 피해를 고정 60으로 변경
- 공식 맥락: 이용자 피드백을 바탕으로 확률형 피해를 제거하고 고정 피해로 변경
- 예상 긍정: 피해 결과 예측 가능성, 실력 중심 전투와의 정합성, 공정성 인식
- 예상 부정: 기존 무기 대비 성능 체감, 반동·연사력과의 조합, 메타 쏠림 우려
- 출시 후 검증: Dragunov 직접 언급 의견의 긍정·부정 비율, 사용률·승률·평균 피해 등

공식 변경 내용은 [PUBG Update 25.2 패치 노트](https://pubg.com/en/news/6616)를
참조한다. 저장된 의견은 공식 문서와 사례 설명을 바탕으로 만든 비식별 합성
데이터이며, 실제 이용자 반응의 정답지로 표시하지 않는다.

### 2.3 제외 범위

- 출시 전 분석에서 아직 존재하지 않는 실제 반응을 사실처럼 제시하지 않는다.
- 처음부터 모든 게임·모든 업데이트 유형의 완전한 범용 스키마를 만들지 않는다.
- 감정 분류만으로 인과효과나 매출·잔존율 변화를 단정하지 않는다.
- Steam·X 외 모든 커뮤니티를 한 번에 연결하지 않는다.
- 원문, 사용자명, 계정 ID, 국가·연령·성별을 저장하거나 추론하지 않는다.
- 업데이트 점검 때문에 기존 이벤트 점검의 계약과 판정 정책을 변경하지 않는다.

## 3. 사용자 흐름과 모드 경계

### 3.1 입력 모드 선택

첫 화면에서 `검토 대상`을 선택한다.

- `이벤트 점검`: 기존 EventBrief 입력과 Black Market·Weekly Supply 사례
- `업데이트 점검`: 아래 UpdateBrief 입력과 Dragunov 저장 사례

업데이트 점검에서 `자료 출처`는 다음 세 가지다.

1. `검증된 저장 데이터`: 기본값. 발표·테스트에 사용
2. `Steam 실시간 갱신`: 선택 시 업데이트 전후 기간을 수집
3. `승인 CSV 가져오기`: 개인정보와 원문 열이 없는 자료만 허용

자료 출처를 바꿀 때 이벤트 입력과 업데이트 입력을 혼동하지 않도록 모드별
프리셋을 별도로 관리한다.

### 3.2 UpdateBrief 입력

공통 입력:

- 게임, 업데이트 이름, 업데이트 유형
- 현재 상태
- 변경 내용
- 변경 목표
- 기대 효과
- 우려 사항
- 적용 범위와 예정일
- 분석 기준일

유형별 추가 입력:

- `weapon_balance`: 대상 무기, 피해량, 반동, 연사력, 탄약, 스폰·사용 모드
- `ui_ux`: 변경 화면, 사용자 동선, 새로 노출되는 정보, 오류 가능성
- `system_rules`: 참여 조건, 보상, 제한, 예외 규칙, 기존 이용자에게 미치는 영향

공통 입력은 모든 유형에서 필요하며, 유형별 필드는 화면에서 선택한 유형에
따라서만 노출한다. 빈 문자열 대신 명시적인 `해당 없음`을 허용해 누락과 실제
부재를 구분한다.

## 4. 산출물 계약과 데이터 흐름

기존 이벤트 계약과 직접 합치지 않고 업데이트 전용 계약을 추가한다. 모든 계약은
기존 `Artifact` 봉투(`run_id`, `schema_version`, `producer`, `input_refs`,
`errors`)를 재사용한다.

```text
UpdateBrief
  → UpdateFeedbackBundle
  → UpdateEvidencePack
  → UpdateImpactAssessment
  → UpdateValidatedDecision
  → UpdateDecisionBrief
```

### 4.1 UpdateBrief

업데이트 기획의 현재 상태와 변경안을 담는다. 출시 전 예상은 이 입력을 기준으로
만 작성한다.

### 4.2 UpdateFeedbackBundle

저장·실시간·CSV 자료를 동일한 입력 봉투로 정규화한다.

- `period`: before, after, 또는 comparable_reference
- `source`, `source_url`, 익명 `source_id`, 언어, 관찰 시점
- 원문 대신 비식별 요약
- `sentiment`: positive, negative, neutral, mixed
- `relevance`: 업데이트 직접 관련성
- `mechanism_tags`: 예측 가능성, 공정성, 성능 체감, 학습 부담 등
- 표본 수와 수집 오류

출시 전 신규 업데이트에는 `after` 실제 반응이 없을 수 있다. 이 경우 `after`를
빈 값으로 채우지 않고 `comparable_reference`로 표시해, 유사한 과거 사례나 공식
사후 맥락을 참고 자료로 구분한다.

### 4.3 UpdateEvidencePack

긍정·부정·혼합 반응을 이용자 유형과 변경 요소에 연결한다.

- 반복되는 긍정 신호
- 반복되는 부정 신호
- 반응이 갈릴 조건
- 이용자 유형별 영향
- 각 주장에 연결된 근거 ID
- 표본 충분성 및 결론 공개 여부

### 4.4 UpdateImpactAssessment

출시 전에 예상되는 영향을 구조화한다.

- `expected_positive`: 예상 긍정 반응
- `expected_negative`: 예상 부정 반응
- `affected_personas`: 영향을 받을 이용자 유형
- `confidence`: 근거 기반 신뢰도
- `validation_metrics`: 출시 후 확인할 지표
- `risks`: 성능·공정성·이해 가능성·동선·예외 처리 등 업데이트 위험

실제 반응 문장과 예상 문장은 필드와 UI에서 구분한다. 예측 항목에는 항상
`예상`, `가능성`, `확인 필요` 표현을 사용한다.

### 4.5 UpdateValidatedDecision와 UpdateDecisionBrief

정책이 입력 표본, 근거 연결, 위험 신뢰도와 필수 확인 지표를 검사한 뒤 다음 중
하나를 결정한다.

- `Go`: 출시 전 위험이 낮고 확인 지표가 정의됨
- `Revise`: 일부 변경안을 수정한 뒤 출시 권장
- `Test`: 실제 출시 전 테스트 서버·A/B·제한 공개가 필요
- `Hold`: 근거 또는 입력이 부족해 판단 보류

기존 이벤트의 `Go / Revise / Hold`와 혼동하지 않도록 업데이트 전용 API와 화면은
한국어 표시를 `출시 가능 / 일부 수정 후 출시 / 테스트 후 출시 / 판정 보류`로
렌더링한다. 내부 enum은 `Go`, `Revise`, `Test`, `Hold`로 고정한다.

## 5. 에이전트 실행 설계

기존 네 에이전트의 실행 시각화와 역할을 재사용하되, 업데이트 모드에서는 각
에이전트가 업데이트 전용 산출물을 만든다.

1. **자료 수집 에이전트**: 기간·출처·업데이트 관련성·감정·비식별 요약을 정규화
2. **변경 영향 분석 에이전트**: 변경 요소별 긍정·부정 신호와 이용자 유형을 묶음
3. **업데이트 레드팀 에이전트**: 출시 전 실패 경로와 예상 반응, 확인 지표 제안
4. **검증·전략 에이전트**: 근거 ID·표본·위험을 검사하고 출시 판정 계산

LLM은 자연어 후보를 만들고 문장을 다듬지만, 다음은 코드가 소유한다.

- 의견의 `before/after/comparable_reference` 구분
- 긍정·부정·중립 라벨 형식과 근거 ID 존재 여부
- 업데이트 유형별 필수 입력
- 예상과 실제 반응의 표시 구분
- 위험 승인·기각과 최종 판정
- 확인 지표와 해당 위험의 연결

실행 이벤트는 기존 `ExecutionEvent` 형식을 그대로 사용한다. 단계·노드·상태·
메시지·정의된 수치를 한국어로 표시하고, 업데이트 모드임을 에이전트 카드에
명확히 표시한다.

## 6. 저장 사례와 실시간 경로

### 6.1 저장 사례

첫 저장 사례는 Dragunov이다. 충분한 시연을 위해 다국어·긍정·부정·중립 요약을
포함하지만, 모두 `synthetic=true`로 표시한다. 사후 실제 반응을 저장 데이터에
섞지 않고, 공식 패치 노트에서 확인 가능한 변경 사실과 공개된 맥락을 별도
`official_context`로 연결한다.

### 6.2 Steam·X 실시간 갱신

실시간 경로는 사용자가 명시적으로 선택했을 때만 실행한다.

- 업데이트 기준일 전후의 기간을 입력받는다.
- Steam과 X에서 공개 자료를 메모리에서 읽는다.
- 즉시 비식별화하고 원문은 저장하지 않는다.
- 최소 표본 미달이면 `Hold` 또는 `Test`로 처리한다.
- X 비용은 기존 프로젝트 예산 가드를 따른다.
- API·네트워크 실패는 오류와 부분 결과로 표시한다.

실시간 데이터가 업데이트 전후 비교를 충분히 제공하지 못하면, 서비스는 결과를
“반응 변화 확인 불가”로 표시해야 한다. 저장된 합성 사례로 자동 대체하지 않는다.

## 7. 화면 설계

업데이트 입력 화면:

- 상단 모드 선택 카드: 이벤트 점검 / 업데이트 점검
- 업데이트 유형 탭 또는 선택 카드: 무기 밸런스 / UI·UX / 시스템·규칙
- 공통 입력 카드와 유형별 입력 카드 분리
- 자료 출처와 저장 사례 선택
- “출시 전 예상이며 실제 반응이 아님” 안내를 실행 버튼 근처에 고정

결과 화면:

1. 출시 판정 배너
2. 예상 긍정 반응 카드
3. 예상 부정 반응 카드
4. 반응이 갈릴 이용자 유형
5. 출시 후 확인 지표 표
6. 근거와 비식별 의견 접기/펼치기
7. 에이전트별 실행 과정과 계약 JSON

`after` 실제 반응이 없는 저장 시연에서는 “업데이트 후 실제 반응” 섹션을 숨기고,
“출시 후 검증할 지표”를 대신 보여준다. 이 문구 규칙은 데이터가 없다는 사실을
결과가 좋아 보이는 것처럼 오해하지 않게 한다.

## 8. 오류·안전·재현성

- 저장 사례는 동일한 입력에서 동일한 핵심 위험·예상 신호·판정을 생성해야 한다.
- LLM의 자연어 표현은 달라도 근거 ID와 정책 판정은 바뀌지 않는다.
- 실시간 의견이 기준일 뒤에 있으면 `cutoff` 오류로 제외한다.
- 표본이 부족하면 긍정·부정 비율을 숨기고 부족 사유를 표시한다.
- 실제 반응이 없는 경우 이를 `0건`으로 해석하지 않고 `없음/미수집`으로 구분한다.
- 모든 외부 자료는 HTTPS URL과 익명 ID를 요구한다.
- API 키·원문·사용자 식별자를 실행 이벤트와 JSONL에 기록하지 않는다.

## 9. 테스트와 완료 기준

최소 테스트는 다음을 포함한다.

- UpdateBrief 유형별 필수 입력과 `해당 없음` 처리
- 저장 Dragunov 사례의 동일 핵심 결과 재현
- 긍정·부정·중립 근거 라벨과 실제 evidence ID 연결 검증
- `comparable_reference`와 실제 `after` 반응 구분
- 표본 부족·cutoff 누출·실시간 연결 실패 시 안전한 `Hold/Test`
- 저장 사례 기본 경로가 외부 API 없이 완주
- React 화면에서 이벤트/업데이트 모드 전환과 결과 라벨 표시
