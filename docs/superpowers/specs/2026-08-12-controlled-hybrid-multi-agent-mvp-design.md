# 게임체인저 통제형 하이브리드 멀티에이전트 MVP 설계

## 1. 결정 요약

게임체인저의 궁극적인 제품 비전은 여러 게임과 이벤트를 분석할 수 있는 범용
서비스다. 다만 남은 교육 기간의 필수 성공 기준은 PUBG: BATTLEGROUNDS의
Black Market 사례 하나를 근거와 함께 안정적으로 분석하는 MVP로 고정한다.

MVP는 검증된 저장 데이터를 기본 입력으로 사용하되, 분석 결과를 미리 저장해
재생하지 않는다. 실행할 때마다 수집, 근거 분석, 레드팀, 감사·전략의 네
에이전트가 실제로 순서대로 동작한다. 실시간 갱신은 별도의 선택 기능으로
제공하고, 외부 API 실패가 기본 시연에 영향을 주지 않게 격리한다.

동일 입력의 핵심 결과는 재현돼야 한다. 문장 표현은 달라질 수 있지만 다음은
같아야 한다.

- 사용된 근거 ID
- 핵심 위험 범주와 등급
- 위험의 승인·기각 결과
- `Go`, `Revise`, `Hold` 최종 판정
- 위험과 수정안의 연결 관계

이를 위해 LLM은 비정형 자료 해석과 설명 작성을 맡고, 근거 검증과 최종 판정은
결정론적 코드가 맡는 통제형 하이브리드 방식을 채택한다.

## 2. 목표와 제외 범위

### 2.1 MVP 목표

- 저장된 Black Market 사례가 네 에이전트를 거쳐 `DecisionBrief`까지 완주한다.
- 실행 중 모든 에이전트와 내부 처리 단계를 실시간으로 펼쳐 보여준다.
- 완료 후 최종 판정을 중심으로 화면을 전환한다.
- 완료된 에이전트별 과정과 근거는 접어두고 선택하면 다시 확인할 수 있다.
- 동일한 저장 입력을 반복 실행했을 때 핵심 결과가 유지된다.
- LLM 또는 실시간 수집이 실패해도 검증된 저장 데이터 경로로 시연할 수 있다.
- 정상적인 `Revise`와 근거 부족에 따른 `Hold`를 모두 설명할 수 있다.

### 2.2 궁극적 제품 비전

범용성은 미리 거대한 프레임워크를 만드는 방식으로 확보하지 않는다. 다음 실제
사례가 요구하는 만큼만 일반화한다.

1. Black Market 사례 완성
2. 두 번째 PUBG 이벤트 추가
3. PUBG 패치 유형 추가
4. 다른 게임 이벤트 추가

공통으로 유지할 것은 `Artifact` 봉투, 근거 ID, 네 에이전트 역할, 감사 규칙,
`DecisionBrief`다. 사례별로 교체할 것은 입력 계약, 위험 분류와 규칙, 프롬프트다.

### 2.3 이번 MVP에서 제외

- 여러 게임과 모든 변경 유형을 동시에 지원하는 범용 입력
- 국가, 성별, 연령대 추정과 교차 세분화
- 모든 커뮤니티 플랫폼 연결
- 에이전트 병렬 실행
- 모델의 숨은 사고 과정 또는 토큰 단위 추론 공개
- LangGraph, 벡터 데이터베이스, 별도 API 서버와 프론트엔드 분리
- 회원가입, 결제, 조직별 권한
- LLM 문장을 매번 완전히 동일하게 만드는 작업

## 3. 전체 아키텍처

기존 `event-preflight` 프로토타입의 Streamlit, Pydantic 계약, 네 에이전트와
오케스트레이터를 재사용한다. 기능을 두 저장소에서 중복 관리하지 않고 팀 기준
저장소인 `game-changer`로 통합한다.

고정 실행 순서는 다음과 같다.

1. 사용자가 `EventBrief`와 데이터 경로를 선택한다.
2. 수집 에이전트가 `FeedbackBundle`을 만든다.
3. 근거 분석 에이전트가 `EvidencePack`을 만든다.
4. 레드팀 에이전트가 `RiskAssessment`를 만든다.
5. 감사·전략 에이전트가 `ValidatedDecision`을 만든다.
6. 오케스트레이터가 `DecisionBrief`를 조립한다.

각 단계는 같은 `run_id`, 고정 `schema_version`, 올바른 생산자, 필수 입력 참조를
유지한다. Pydantic은 형식을 검사하고, 별도의 의미 검증은 모든 위험과
페르소나가 실제 근거 ID만 참조하는지 검사한다.

역할의 경계는 다음과 같다.

| 구성 요소 | 책임 |
| --- | --- |
| 입력 계층 | `EventBrief`, 저장 fixture 또는 실시간 수집 설정 준비 |
| 오케스트레이터 | 네 에이전트의 고정 순서, 상태, 재시도와 중단 관리 |
| 수집 에이전트 | 출처 확인, 컷오프, 비식별화, 표본 집계 |
| 근거 분석 에이전트 | 중복 제거, 관련 근거 검색, 문제 묶기, 언어권 판정, 페르소나 구성 |
| 레드팀 에이전트 | 실패 경로, 영향 대상, 위험 후보와 설명 작성 |
| 감사·전략 에이전트 | 근거 대조, 위험 승인·기각, 수정 우선순위 구성 |
| 결정론적 정책 | 표본 기준, 위험 등급, `Go / Revise / Hold` 판정 |
| Streamlit 화면 | 실행 과정과 최종 결과의 두 상태 표현 |
| JSONL 실행 기록 | 비식별 단계 산출물, 오류와 중단 지점 기록 |

## 4. 에이전트별 내부 데이터 흐름

화면에는 모델의 숨은 추론을 노출하지 않는다. 실제로 시작하거나 완료된 처리
단계와 검증된 중간 산출물만 표시한다.

### 4.1 수집 에이전트

처리 노드는 다음 순서다.

1. 저장 데이터 또는 실시간 출처 선택
2. 승인 CSV, Steam, X의 출처와 형식 확인
3. 분석 기준 시점 이후 자료 제외
4. 사용자 식별 정보 제거 및 비식별 ID 생성
5. 메커니즘 태그와 짧은 비식별 요약 생성
6. 언어권별 일반 표본과 메커니즘 표본 집계
7. `FeedbackBundle` 계약 검사

실행 중에는 출처, 수집 건수, 제외 건수, 언어권별 표본과 오류를 표시한다.

### 4.2 근거 분석 에이전트

처리 노드는 다음 순서다.

1. 같은 자료의 중복 제거
2. 이벤트 기획과 관련된 근거 검색 및 순위화
3. 반복되는 문제를 위험 원인 범주로 묶기
4. 언어권별 최소 표본 기준 적용
5. 표본이 부족한 언어권의 고유 결론 숨기기
6. 네 행동형 페르소나와 각 페르소나의 근거 구성
7. `EvidencePack` 계약과 모든 근거 ID 검사

실행 중에는 중복 제거 수, 발견한 문제 범주, 숨긴 언어권과 페르소나별 근거 수를
표시한다.

### 4.3 레드팀 에이전트

처리 노드는 다음 순서다.

1. 이벤트의 참여, 반복, 보상, 확률, 과금과 만료 구조 검토
2. 이용자가 겪을 실패 경로 작성
3. 영향을 받을 페르소나와 언어권 연결
4. 근거가 연결된 위험 후보 작성
5. 고정 분류표로 위험 범주와 등급 부여
6. `RiskAssessment` 계약과 근거 참조 검사

실행 중에는 위험 후보, 영향 대상, 등급, 연결된 근거 수를 표시한다.

### 4.4 감사·전략 에이전트

처리 노드는 다음 순서다.

1. 모든 위험이 실제 근거 ID를 참조하는지 확인
2. 위험 신뢰도와 최소 기준 확인
3. 기준을 충족한 위험 승인, 나머지 위험 기각
4. 언어권별 표본 규칙 적용
5. 결정론적 정책으로 `Go`, `Revise`, `Hold` 계산
6. 승인된 위험별 수정안과 성공 지표 구성
7. `ValidatedDecision` 계약 검사

실행 중에는 승인·기각 위험, 기각 이유, 적용된 판정 규칙과 수정 우선순위를
표시한다.

### 4.5 오케스트레이터

오케스트레이터는 각 단계의 계약을 검사하고 다음 입력으로 전달한다. 단계별
산출물을 기록한 뒤 상위 위험을 정렬하고, 페르소나별 반응과 수정안을 조립해
`DecisionBrief`를 만든다. 최종 브리프가 생성된 뒤에만 회고형 평가 정답지를
읽는다.

## 5. 실행 시각화와 화면 상태

### 5.1 실행 중 화면

- 네 에이전트 카드를 모두 펼친다.
- 처리 순서를 연결선으로 나타내고 현재 노드만 강조한다.
- 완료된 노드는 체크, 실행 중은 움직이는 표시, 이후 노드는 대기로 표시한다.
- 완료된 에이전트의 중간 결과도 전체 파이프라인이 끝날 때까지 펼쳐둔다.
- 각 카드에서 현재 내부 노드, 짧은 결과, 주요 건수와 입출력 계약을 보여준다.
- 상태는 `대기`, `실행 중`, `완료`, `재시도`, `실패`만 사용한다.

기존 `(stage, status, message)` 콜백은 에이전트, 내부 노드, 상태, 짧은 사용자용
요약과 구조화된 수치를 전달하는 실행 이벤트로 확장한다. 별도 이벤트 서버나
WebSocket은 추가하지 않고 Streamlit의 자리표시자 영역을 갱신한다.

결정론적 안전 경로가 빠르게 끝나는 경우 가짜 대기 시간을 넣지 않는다. 완료된
실제 실행 기록을 즉시 보여준다.

### 5.2 실행 완료 화면

- `Go`, `Revise`, `Hold` 판정을 화면의 가장 중요한 정보로 표시한다.
- 핵심 위험, 연결 근거, 권장 수정안을 바로 보여준다.
- 실행 과정은 `에이전트 처리 과정 및 근거` 아래 네 개의 접힌 항목으로 이동한다.
- 사용자가 항목을 선택하면 실행 중 보았던 중간 산출물과 근거를 다시 확인한다.
- 사람의 최종 의사결정임을 명시하고 자동 실행 또는 자동 배포처럼 표현하지 않는다.

## 6. LLM 역할과 재현성

### 6.1 역할 분리

항상 결정론적 핵심 결과를 먼저 만들고 LLM이 설명을 보강한다.

1. 코드가 중복 제거, 표본 판정과 핵심 위험 범주를 계산한다.
2. LLM이 허용된 근거 안에서 위험 설명과 이용자 반응 초안을 작성한다.
3. 코드가 LLM이 참조한 모든 근거 ID를 실제 데이터와 대조한다.
4. 존재하지 않는 근거와 기준 미달 위험을 기각한다.
5. 코드가 고정 정책으로 위험 등급과 최종 판정을 계산한다.
6. LLM이 승인된 결과를 바탕으로 읽기 쉬운 설명을 작성한다.
7. 코드가 구조와 참조 관계를 다시 검사해 최종 브리프를 조립한다.

LLM은 `run_id`, 생산자, 입력 참조, 위험 등급과 최종 판정을 작성하지 않는다.
새로운 위험을 제안할 수는 있지만 즉시 판정에 반영하지 않고 `추가 탐색
인사이트`로 분리한다. 정식 분류와 근거 기준을 충족한 뒤에만 핵심 위험으로
승격한다.

### 6.2 같은 입력의 정의

- 저장 데이터는 같은 fixture 버전과 같은 `EventBrief`를 뜻한다.
- 실시간 데이터는 같은 검색어가 아니라 같은 시점에 저장된 `FeedbackBundle`
  스냅샷을 뜻한다.
- 새 실시간 갱신은 새로운 입력이므로 결과가 달라질 수 있다.
- `run_id`, 실행 시간과 표현 문장은 재현성 비교에서 제외한다.

반복 검증은 위험 범주와 등급, 위험별 근거 ID, 승인·기각 결과, 최종 판정,
위험과 수정안의 연결만 비교한다.

### 6.3 결정 정책

- 승인된 Critical 위험이 하나라도 있으면 `Hold`
- 세 언어권 이상이 최소 표본에 미달하면 `Hold`
- 승인된 High 위험이 하나라도 있으면 `Revise`
- 일부 언어권만 표본 미달이면 `Revise`
- 그 외에는 `Go`

## 7. 저장 데이터와 실시간 갱신의 격리

기본 실행은 검증된 저장 fixture를 사용한다. 실시간 실행은 별도 선택으로
시작하며 새로운 `run_id`와 입력 스냅샷을 가진다.

- 실시간 실패가 이전 저장 데이터 결과를 삭제하거나 덮어쓰지 않는다.
- 새 실행을 시작할 때 화면의 이전 결과는 현재 결과 영역에서 제거한다.
- 외부 인증, 예산 또는 출처 오류는 실시간 실행만 중단한다.
- 사용자는 즉시 저장 데이터 안전 경로로 다시 실행할 수 있다.
- 실시간 표본이 부족하면 억지 결론 대신 정상적인 `Hold`를 반환한다.
- 원문과 사용자명은 저장하지 않고 비식별 요약과 근거 ID만 기록한다.

MVP의 필수 실연동 검증은 Steam 또는 승인 CSV 하나면 충분하다. X 연동은 인증과
비용 변수가 있으므로 핵심 경로가 준비된 뒤의 선택 작업이다.

## 8. 오류 처리와 안전한 대체 실행

| 상황 | 처리 | 사용자 표시 |
| --- | --- | --- |
| 입력 형식 오류 | 실행 전에 차단 | 수정할 입력란과 이유 |
| LLM 응답 오류 또는 거절 | 한 번 재시도 | 재시도 중 |
| LLM 재시도 실패 | 규칙 기반 결과로 계속 | 안전 경로 전환과 영향 범위 |
| 존재하지 않는 근거 참조 | 해당 위험 기각 | 근거 ID와 기각 이유 |
| 신뢰도 기준 미달 | 해당 위험 기각 | 신뢰도 부족 |
| 언어권 표본 부족 | 고유 결론 숨김 | 현재 건수와 최소 기준 |
| 세 언어권 이상 부족 | `Hold` | 오류가 아닌 근거 부족 |
| 실시간 API 인증·예산 오류 | 실시간 실행 중단 | 저장 데이터 실행 안내 |
| 계약 위반 | 즉시 파이프라인 중단 | 실패 단계와 오류 코드 |
| 예상하지 못한 오류 | 이후 단계 미실행 | `run_id`와 재실행 안내 |

LLM 실패로 규칙 기반 결과를 사용했다면 숨기지 않는다. 핵심 근거와 판정은
결정론적 경로가 보장하지만 AI 설명이 생략되거나 기본 문장으로 대체됐음을
명시한다. 계약 위반처럼 결과의 신뢰성을 보장할 수 없는 오류는 대체 결과를
만들지 않고 중단한다.

## 9. 검증과 완료 기준

### 9.1 종단 및 계약 검증

- 저장된 Black Market 데이터가 네 단계를 거쳐 `DecisionBrief`를 생성한다.
- 각 산출물의 스키마, `run_id`, 생산자와 입력 참조를 검사한다.
- 모든 위험, 페르소나와 수정안의 참조가 실제 ID 집합에 존재한다.
- 컷오프 이후 근거와 개인정보 필드는 통과하지 못한다.

### 9.2 재현성 검증

같은 fixture와 `EventBrief`를 서로 다른 `run_id`로 두 번 실행하고 실행 메타데이터와
표현 문장을 제외한 다음 항목을 비교한다.

- 위험 범주와 등급
- 위험별 근거 ID
- 승인·기각 결과
- 최종 판정
- 위험과 수정안의 연결

### 9.3 시각화 검증

- 발표자가 현재 에이전트와 내부 노드를 식별할 수 있다.
- 앞 단계의 출력이 다음 단계의 입력이 되는 흐름을 확인할 수 있다.
- 완료, 대기, 재시도와 실패 상태가 서로 구분된다.
- 감사 에이전트의 승인·기각 이유가 보인다.
- 완료 후 최종 결과 중심으로 전환되고 과정은 다시 펼칠 수 있다.

### 9.4 필수 시나리오

- 충분한 근거가 있는 `Revise`
- 세 언어권 이상 근거 부족에 따른 `Hold`
- 존재하지 않는 근거를 감사 단계가 기각
- LLM 실패 후 규칙 기반 안전 경로로 완료
- 실시간 수집 실패 후 저장 데이터 실행 가능

### 9.5 발표 준비

- 배포본, 로컬본, 백업 녹화본을 준비한다.
- 시연 결과를 미리 재생하는 것이 아님을 중간 산출물로 설명할 수 있다.
- 강사용 설명은 "AI는 분석가, 프로그램은 심사위원·감사자"라는 비유를 쓴다.

## 10. 우선순위형 실행 순서

고정된 주차별 일정으로 묶지 않는다. 앞선 의존성이 해결되면 같은 날이라도 바로
다음 단계로 이동하며, 작업은 아래 우선순위로 진행한다.

### P0. 기준 코드 통합과 범위 동결

- 팀 기준 저장소를 `game-changer`로 확정한다.
- 검증된 `event-preflight` 코드를 한 번만 통합한다.
- Black Market 저장 데이터와 현재 23개 테스트가 그대로 통과하게 한다.
- 한 사례, 한 입력 계약, 고정된 네 에이전트라는 MVP 경계를 동결한다.

### P1. 실제 실행 과정 시각화

- 기존 단계 콜백을 내부 노드 실행 이벤트로 확장한다.
- 네 에이전트 카드, 상태와 중간 결과를 실행 중 펼쳐 보여준다.
- 완료 후 최종 결과 중심 화면과 접힌 실행 기록을 제공한다.

### P2. 하이브리드 재현성 보장

- LLM의 설명 생성과 코드의 판정을 분리한다.
- 최종 근거 ID 대조와 결정론적 감사 정책을 항상 적용한다.
- 서로 다른 `run_id`의 반복 실행 불변성 검사를 추가한다.

### P3. 오류와 실시간 경로 격리

- `Hold`, 잘못된 근거, LLM 실패를 검증한다.
- 실시간 실패가 저장 데이터 실행과 이전 정상 결과를 훼손하지 않게 한다.
- Steam 또는 승인 CSV 한 경로를 필수 실연동으로 검증한다.

### P4. 배포와 발표 안정화

- 전체 자동 검증과 배포 환경을 확인한다.
- 배포본, 로컬본, 백업 녹화본으로 반복 리허설한다.
- 화면의 설명과 중간 결과 가독성을 다듬는다.

### P5. 준비된 경우에만 확장

- 두 번째 이벤트 fixture를 추가한다.
- 그 사례가 실제로 요구하는 공통 경계만 추출한다.
- X 실제 연동, 실행 스냅샷·모델·프롬프트 버전 표시는 시간이 남을 때 진행한다.

P5가 끝나지 않아도 P0부터 P4까지 충족하면 MVP는 완료다.

## 11. 강사에게 설명할 핵심 문장

> 범위는 한 사례로 줄였지만 멀티에이전트의 깊이는 유지했고, AI의 표현 능력은
> 활용하되 핵심 판단은 규칙으로 고정하도록 변경했습니다.

저장된 것은 결과가 아니라 입력 자료다. 네 에이전트는 매 실행마다 실제로
동작한다. AI는 형식이 일정하지 않은 자료를 해석하고 읽기 쉬운 설명을 작성한다.
프로그램은 실제 근거, 표본과 안전 규칙을 확인한 뒤 최종 판정을 내린다. 따라서
표현은 달라져도 같은 입력의 근거, 핵심 위험과 최종 판정은 유지된다.
